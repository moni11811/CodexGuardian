# Alternative Agent Recovery Projects

Research date: 2026-07-26.

## Decision

Do not merge OpenParsec and Farfield into one app.

Keep Guardian, but narrow its job: durable recovery coordinator for the real Codex Desktop task. Put remote chat, approvals, files, and diffs above it.

Best choices by goal:

| Goal | Best reference | Why | Catch |
| --- | --- | --- | --- |

| Fork permissive mobile code | [CC Pocket](https://github.com/K9i-0/ccpocket) | MIT, native clients, launchd bridge, offline resend, approvals, git, worktrees. | Its bridge owns CLI sessions. Hard-restart correctness is not its purpose. |

| Observe/control Codex Desktop | [Farfield](https://github.com/achimala/farfield) plus [Codex app-server](https://github.com/openai/codex/blob/main/codex-rs/app-server/README.md) | Native protocol, thread/turn events, interrupt, model/reasoning controls, generated schemas. | Farfield has no durable restart state and no built-in remote authentication. |

| Restart discipline | [Erlang/OTP](https://www.erlang.org/doc/system/sup_princ.html), [Kubernetes probes](https://kubernetes.io/docs/concepts/configuration/liveness-readiness-startup-probes/), launchd | Restart trees, intensity limits, startup/readiness/liveness separation. | They supervise processes, not Codex task meaning. |
| Phone attention UX | [Yep Anywhere](https://github.com/kzahel/yepanywhere) | Needs Attention / Active / Recent inbox, global activity, E2E relay, lock-screen approvals. | It piggybacks agent history; no exact Desktop recovery transaction. |

No reviewed project guarantees this whole invariant:

> Wait until every unrelated Codex task is safe, restart the shared Desktop runtime, reopen the exact requesting task, deliver one continuation once, and prove that same task started it.

That remains Guardian’s useful differentiator.

## Bug theory

The repeated waiting is not mainly a delay bug. Guardian mixes four different facts:

1. Is the macOS process alive?
2. Is the Codex control plane responsive?
3. Is a specific thread working, awaiting input, or idle?
4. Did the recovery workflow durably cross its next transition?

JSONL tail age and a PID cannot answer all four. A task asking Guardian to restart can also keep itself active, creating a circular wait. Multiple live tasks expose the deeper missing pieces: authoritative task state, one durable coordinator, generation fencing, and a global safe-point scheduler.

## Local feasibility check

The installed environment already exposes a stronger route than log inference:

- Global CLI: `codex-cli 0.142.0`.
- Codex Desktop bundled CLI: `0.146.0-alpha.3.1`.
- Bundled CLI supports `codex app-server proxy --sock`.
- Codex Desktop owns `~/.codex/ipc/ipc.sock`.
- Current upstream Codex app-server schemas expose loaded-thread listing, thread status events, turn start/steer/interrupt, approval resolution, MCP startup state, and client message correlation.
- Current Guardian source has a menu app and an MCP executable, but no separate always-on coordinator daemon target.

Conclusion: direct Desktop observation is feasible, and Farfield demonstrates the adapter shape. Guardian must still test the installed Desktop socket against schemas generated by that bundled Codex binary. Once proven, native events should replace JSONL inference, not merely supplement another timer.

## Protocol and state lessons

### Codex app-server first

The official [app-server protocol](https://github.com/openai/codex/blob/main/codex-rs/app-server/README.md) now provides the strongest available evidence:

- `thread/loaded/list` and `thread/status/changed` identify loaded, idle, active, and system-error threads.
- `turn/started`, item progress, and `turn/completed` provide a real lifecycle.
- Approval and input requests remain open until `serverRequest/resolved`.
- `mcpServer/startupStatus/updated` separates tool startup from turn health.
- `turn/steer` and `turn/interrupt` allow per-task repair before a global restart.
- `config/mcpServer/reload` may repair a tool registry without restarting Desktop.
- `clientUserMessageId` can correlate a durable outbox entry with the user-message item the target thread accepted.
- The local Unix control path is intended for control-plane clients. The WebSocket listener remains experimental; do not expose it directly.
- Built-in `remoteControl/*` exists but is experimental. Feature-detect it and track upstream rather than assuming a stable production contract.

If upstream remote control becomes stable and proves exact Desktop-thread attachment, use it for pairing and transport. Keep Guardian as the local recovery policy and durable journal instead of maintaining a competing relay.

Guardian should vendor the schema generated by the installed Codex binary, validate every message, and keep adapters per supported protocol version. Unknown schema means observe-only or fail closed.

### AHP above ACP

[ACP](https://github.com/agentclientprotocol/agent-client-protocol) solves one client talking to one agent. Guardian’s remote controller needs multiple clients observing shared sessions.

[AHP](https://microsoft.github.io/agent-host-protocol/guide/ahp-and-acp.html) fits that upper layer:

- one host owns authoritative session state;
- clients subscribe to immutable channel snapshots;
- actions carry client identity and server sequence;
- pending local actions reconcile only after the server echoes them;
- reconnect replays missed actions or sends a fresh snapshot;
- `InputNeeded` is distinct from `InProgress`;
- queued and steering messages have stable IDs;
- Swift, Kotlin, TypeScript, Rust, and Go clients already exist.

Use an internal Guardian state model shaped like AHP. Offer an AHP adapter later. AHP is still draft, so Guardian’s SQLite schema must not equal the wire schema.

### MCP is an adapter, not the owner

MCP is correct for `prepare_recovery`, `status`, `restart`, and `ack` tools. It is wrong as the only always-on supervisor. Codex can kill or disconnect the MCP process it invoked.

Required split:

```text
Codex MCP client ─┐
Menu-bar app ─────┼──> Guardian daemon ──> Codex Desktop adapter
iPhone/Web ───────┘          │             ├─ native IPC/app-server
                             │             ├─ ACP agent adapter
                             │             └─ PTY fallback, observe-only
                             └─ SQLite journal + event stream
```

The daemon runs under launchd. The menu app and MCP executable become replaceable thin clients.

## Durable workflow lessons

| System | Pattern to take | Do not take |
| --- | --- | --- |
| [Temporal](https://docs.temporal.io/encyclopedia/detecting-activity-failures) | Per-attempt deadlines, progress heartbeats with details, retry classification, idempotent activities. | Server cluster and deterministic workflow runtime. |
| [Restate](https://docs.restate.dev/concepts/durable_execution) | Journal the result of each side effect; replay skips completed work; durable promises and timers. | Separate distributed runtime. |
| [Hatchet](https://docs.hatchet.run/v1/durable-execution) | Scoped idempotency keys, worker health, capacity and fairness, checkpoints. | Full task platform. |
| [DBOS](https://github.com/dbos-inc) | Unique workflow IDs, checkpoints, notifications, exactly-once transaction boundaries. | PostgreSQL dependency for a local menu helper. |
| [LangGraph interrupts](https://langchain-ai.github.io/langgraph/how-tos/human_in_the_loop/breakpoints/) | Explicit durable human-input pause and resume cursor. | LLM graph runtime; resumed nodes can rerun, so it does not remove idempotency work. |
| [Erlang/OTP](https://www.erlang.org/doc/system/sup_princ.html) | One-for-one hierarchy, maximum restart intensity, escalation to parent. | Treating every failure as a child crash. |
| [Kubernetes probes](https://kubernetes.io/docs/concepts/configuration/liveness-readiness-startup-probes/) | Separate startup, readiness, liveness, and progress. | Polling timers as semantic task truth. |
| [launchd](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingLaunchdJobs.html) / [systemd](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html) | Keep daemon alive, rate-limit crash loops, clean process ownership. | Using process survival as task correctness. |

Implement these semantics locally with SQLite WAL. Do not embed a workflow platform.

## Required Guardian state model

Every observed task state needs `source`, `observedAt`, `generation`, and `confidence`.

| State | Meaning | Destructive restart allowed? |
| --- | --- | --- |
| `working` | Active turn plus recent protocol progress. | No. |
| `waiting_user` | Unresolved approval, question, auth, or permission request. | No. Notify. |
| `slow` | Active, responsive control plane, no progress beyond a tool-specific soft deadline. | No. Diagnose or ask. |
| `stuck` | Active, no pending input, hard progress deadline exceeded, control-plane probe or owned worker failed. | Only through escalation policy. |
| `idle` | Loaded and able to accept input; no active turn. | Yes, if no owned background work. |
| `finished` | Terminal turn and no queued/background work. | Yes. |
| `recovering` | Durable recovery transaction owns this task. | Only its fenced recovery owner may act. |
| `unknown` | Snapshot stale, schema unsupported, connection lost, or evidence conflicts. | No. Fail closed. |

“No output for N seconds” is never enough to call a task stuck. Long compiles, downloads, tool calls, and subagents can be quiet while healthy.

## Safe restart scheduler

Before killing Desktop:

1. Persist request, origin thread, continuation, and unique operation ID.
2. Acquire a daemon lease with owner, generation, expiry, and renewal.
3. Take one authoritative snapshot of all loaded threads, active turns, unresolved requests, queued messages, and owned background terminals.
4. Classify the requesting task and every unrelated task.
5. Block on any `working`, `waiting_user`, `slow`, `recovering`, or `unknown` unrelated task.
6. Ignore only the verified recovery heartbeat for this origin. Real resumed work in that same thread blocks again.
7. Re-read the server generation immediately before termination. Any change invalidates the decision and restarts evaluation.
8. Persist `restart_issued` before the side effect.
9. After launch, prove process startup, control-plane handshake, schema compatibility, plugin readiness, and target-thread load separately.
10. Send continuation from a durable outbox with `clientUserMessageId = operation ID`.
11. After an ambiguous disconnect, search that thread's stored items for the operation ID before resending. Finding it means attach to that turn; do not create another.
12. Keep the outbox item until the same thread emits the matching user-message item and `turn/started`.
13. ACK only after meaningful progress. Otherwise retry by policy or dead-letter visibly.

Recovery journal:

```text
prepared -> gated -> restart_issued -> desktop_started -> control_ready
         -> target_loaded -> continuation_sent -> same_thread_accepted
         -> progress_seen -> acknowledged
```

Every transition is transactional and idempotent. A crash after any arrow must resume from stored state without repeating an unsafe side effect.

## Escalation ladder

Global Desktop restart is last, not first:

1. Classify failure: tool, MCP host, app-server, thread, Desktop, permission, or external service.
2. Retry once only when evidence says transient, with jitter and a deadline.
3. Reload or reconnect the affected MCP/tool host.
4. Interrupt or steer only the affected turn.
5. Restart the app-server/control connection if it is independently owned.
6. Restart Desktop only at a proven global safe point.
7. Open a circuit after bounded failures; require explicit human reset.

Store failure class, changed corrective variable, result, and next allowed attempt time. Never repeat an unchanged deterministic action.

## What Guardian is still missing

### P0 — recovery correctness

1. Direct, versioned Codex Desktop protocol adapter. Remove JSONL-tail activity from the restart authority path.
2. Separate launchd Guardian daemon. MCP and menu app become clients.
3. SQLite WAL event journal and durable outbox.
4. Server generation, monotonic event sequence, reconnect replay/full snapshot, and stale-command fencing.
5. Exact continuation ACK based on matching thread + client message ID + `turn/started`, not heartbeat text alone.
6. Global safe-point scheduler over every loaded task, approval, queue, subagent, and background terminal.
7. Restart hierarchy, bounded attempts, exponential cooldown, hourly budget, circuit breaker, manual reset.
8. Per-operation deadlines. Disconnect rejects all in-flight calls.
9. Explicit readiness: Desktop process, protocol handshake, schema, target thread, MCP/plugin state.
10. Fault injection at every journal transition.

### P1 — useful controller

1. One attention inbox across tasks: needs approval, needs answer, failed, suspected stuck, recovery pending.
2. Per-task actions: prompt, steer, interrupt, retry tool, approve, deny, reload MCP, checkpoint, restart.
3. Restart impact preview: exactly which tasks block and why.
4. Worktree/process ownership so one task cannot damage another task’s workspace.
5. Secure QR pairing, per-device keys, capability scopes, revocation, rotation, audit trail.
6. Encrypted transport; no prompt content in push notifications.
7. Full snapshot after reconnect and offline command queue with explicit server ACK.
8. Diff, last green commit, dirty-tree, and rollback checkpoint before destructive recovery.

### P2 — smart Guardian

Apple’s [Foundation Models framework](https://developer.apple.com/documentation/foundationmodels/) is useful for:

- summarizing the last verified task events;
- classifying the likely failure family;
- drafting a continuation prompt;
- explaining why restart is blocked;
- recommending the next non-destructive diagnostic.

Use guided generation into a strict Swift type. Feed only bounded, redacted state. The model must never determine liveness, override `unknown`, authorize a restart, select secrets, or invent an ACK. Deterministic protocol evidence remains authority.

## Regression suite required before implementation

Write these red first:

1. Unrelated active thread blocks global restart.
2. Unresolved approval and MCP authentication both classify as `waiting_user`, not `stuck`.
3. Quiet but progressing long tool does not trip the hard deadline.
4. Sequence gap forces a full snapshot before any destructive command.
5. Stale generation invalidates a previously safe restart decision.
6. Daemon crash before and after every journal transition resumes correctly.
7. Crash after send but before ACK does not create a second turn.
8. Duplicate MCP caller and duplicate phone command share one operation ID and one owner.
9. Lease expiry fences the stale process.
10. App-server disconnect fails all pending calls by deadline.
11. Wrong-thread or wrong-message ACK fails closed.
12. Corrupt queue row, disk-full, permission loss, and unsupported schema do not poison unrelated tasks.
13. Restart budget survives daemon and machine restart.
14. Tool reload success prevents unnecessary Desktop restart.
15. Local-model output cannot invoke restart or alter deterministic state.

## Licensing boundary

Guardian uses PolyForm Noncommercial. That is public source-available software, not OSI open source.

- MIT/Apache projects such as Farfield, CC Pocket, Happy, Yep Anywhere, AgentAPI, Harnss, AHP, ACP, and Codex are the safest code references when their notices and terms are preserved.
- AGPL projects such as Paseo and Codexia should be treated as architecture references unless Guardian’s distribution license changes or the component remains a properly separated service.
- OpenParsec is GPL-3. Do not merge its code into the PolyForm application without a license review. A separately installed break-glass client is safer.
- Never copy implementation from a project merely because its interface is visible. Record source, license, commit, and retained notice for every adopted component.

This section is engineering risk guidance, not legal advice.

## Rejected directions

- OpenParsec/pixel streaming as the control plane.
- Runtime-patching Codex Electron bundles to expose the GUI.
- Clipboard paste, Accessibility keystrokes, or terminal TUI scraping as recovery proof.
- `codex exec resume`; it creates a detached worker, not the same Desktop task.
- Public unauthenticated Farfield/AgentAPI ports.
- MCP server as the only supervisor.
- Local AI deciding whether work is alive or safe to kill.
- Unlimited retry or fixed-delay restart loops.
- Importing Temporal/Restate/DBOS merely to avoid writing a small local journal.

## Recommended build order

1. Codex Desktop protocol observer, generated schemas, and red state-classification tests.
2. launchd daemon plus SQLite journal/outbox; move ownership out of MCP.
3. Safe-point scheduler, generation fencing, exact ACK, circuit breaker, chaos tests.
4. Per-task repair actions and attention inbox in the existing macOS app.
5. Secure remote API shaped like AHP; reuse CC Pocket/Remodex/Yep UX and security lessons.
6. Native iPhone client only after reconnect, ACK, and authorization tests pass.
7. Foundation Models advisory summaries and continuation suggestions last.
